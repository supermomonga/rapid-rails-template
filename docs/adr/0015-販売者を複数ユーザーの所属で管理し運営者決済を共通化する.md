# 販売者を複数ユーザーの所属で管理し運営者決済を共通化する

## Context and Problem Statement

個人User所有の販売者では共同運営と複数販売者への参加ができない。運営者専用プランは権限・送金・設定の分岐を持ち、同じ販売業務を二重に実装する必要があった。

## Decision Drivers

* 販売主体と操作するユーザーを分離する
* アプリ管理者権限を販売者の操作権限として暗黙に利用しない
* 継続契約を維持しながら担当の交代と販売者の閉鎖を扱う
* 販売者機能の利用資格、所属の役割、個別料率を独立させる

## Considered Options

* 個人所有の販売者へ共同管理者だけを追加する
* ホスト全体の汎用組織機能を作る
* Billing内の販売者アカウントと多対多の所属で統一する

## Decision Outcome

Billing::MerchantAccountとBilling::MerchantMembershipをEngine内に置く。販売者管理者・担当者・閲覧者で認可し、運営も通常の販売者として所属する。全プランを販売者に所属させ、運営者専用区分を廃止する。全体料率とアプリ管理者が指定する販売者別料率を請求時に解決し、分配条件を保存する。

アプリ管理者限定は既存所属にも作用する利用資格の設定とし、所属情報や請求を削除しない。未閉鎖の各販売者には操作可能な管理者を最低1人残し、所属とホスト権限の変更でも同じ制約を適用する。閉鎖は新規受付・更新の停止から非同期に進め、利用期間と未完了取引が残る間は完了しない。

操作対象をURLに固定し、前回選択だけをUserに保持する。操作履歴は通知から分離し、通常変更は履歴のみ、対応が必要な事象だけを利用可能な所属者全員へ通知する。新規生成だけを対象とし、旧データの移行・互換経路は作らない。

### Consequences

* Good, because 個人・共同運営・運営自身の販売で決済処理と画面を共有できる。
* Good, because 担当者が退会しても販売者と契約履歴を保持できる。
* Bad, because 最後の管理者、利用制限、契約開始・閉鎖の競合をEngineとホストにまたがって検証する必要がある。

### Confirmation

役割・非所属・限定設定・招待・管理者の同時脱退・閉鎖と請求の競合を検証する。4チェーンで0%・個別料率・同一送金先を確認し、複数販売者のdesktop/mobile切替と履歴を撮影する。

## More Information

現在の振る舞いは[サブスク決済](../reference/billing.md)を正本とする。アプリ全体の組織、組織による購入、閉鎖の取消・再開は対象外とする。
